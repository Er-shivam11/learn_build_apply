# Phase 5 — Database Design

Database design is about organizing data for correctness, performance, and scalability. A good design reduces redundancy, improves maintainability, and balances read/write performance.

---

# 34. Normalization

## Definition

**Normalization is the process of organizing data into multiple related tables to eliminate redundancy and improve data integrity.**

---

## Why

Without normalization:

* Duplicate data
* Update anomalies
* Insert/Delete anomalies
* Wasted storage

---

## Analogy

Instead of writing the same student's address on every exam paper,

store the address once,

and reference it whenever needed.

---

## Example (Not Normalized)

```text
Orders

OrderID | Customer | City    | Product
--------+----------+---------+---------
101     | Shivam   | Mumbai  | Laptop
102     | Shivam   | Mumbai  | Mouse
103     | Shivam   | Mumbai  | Monitor
```

City is repeated unnecessarily.

---

## Better Design

```text
Customers

CustomerID | Name   | City
-----------+--------+--------
1          | Shivam | Mumbai

Orders

OrderID | CustomerID | Product
--------+------------+---------
101     | 1          | Laptop
102     | 1          | Mouse
103     | 1          | Monitor
```

---

## Execution

```text
Repeated Data
      ↓
Separate Tables
      ↓
Relationships
      ↓
Less Duplication
```

---

## Drawbacks

* More JOINs
* Slightly slower reads
* More complex queries

---

## Quick Revision

* Reduce redundancy
* Better integrity
* More JOINs

---

# 35. Denormalization

## Definition

**Denormalization intentionally duplicates data to improve query performance and reduce JOIN operations.**

---

## Why

Analytics systems read data much more than they write it.

Fewer JOINs means faster reports.

---

## Analogy

Keeping a photocopy of an important document.

Original still exists,

but reading the copy is faster.

---

## Example

```text
Orders

OrderID

CustomerName

City

Product

Amount
```

Customer information is repeated.

Reads become faster.

---

## Execution

```text
Normalized Tables
       ↓
Duplicate Frequently Used Data
       ↓
Fewer JOINs
       ↓
Faster Reads
```

---

## Drawbacks

* Duplicate data
* Higher storage
* Updates become harder

---

## Quick Revision

* Duplicate Data
* Faster Reads
* Slower Updates

---

# 36. Partitioning

## Definition

**Partitioning divides a large table into smaller physical pieces while appearing as one logical table.**

---

## Why

Scanning a billion-row table is slow.

Partitioning allows PostgreSQL to scan only the required partition.

---

## Analogy

A library stores books by year.

Looking for a 2026 book?

Go directly to the 2026 shelf.

No need to search every shelf.

---

## Example

Orders table

```text
Orders_2024

Orders_2025

Orders_2026
```

Query

```sql
SELECT *

FROM orders

WHERE order_date >= '2026-01-01';
```

Only the 2026 partition is scanned.

---

## Execution

```text
Orders

↓

Partition by Year

↓

2024

2025

2026

↓

Scan One Partition
```

---

## Drawbacks

* More administration
* Wrong partition strategy can reduce benefits

---

## Quick Revision

* Large Tables
* Faster Scans
* Partition Pruning

---

# 37. Views

## Definition

**A View is a virtual table created from a SQL query. It stores the query, not the data.**

---

## Why

Hide complex SQL.

Provide security.

Reuse business logic.

---

## Analogy

A saved filter in Excel.

The original spreadsheet stays the same,

but you always see filtered data.

---

## Syntax

```sql
CREATE VIEW high_value_orders AS

SELECT *

FROM orders

WHERE amount > 10000;
```

---

## Execution

```text
User

↓

View

↓

Original Table
```

Whenever the base table changes,

the view reflects the latest data.

---

## Drawbacks

* Doesn't improve performance.
* Complex views may become slow.

---

## Quick Revision

* Virtual Table
* Stores Query
* Not Data

---

# 38. Materialized Views

## Definition

**A Materialized View stores the actual query result physically on disk instead of executing the query every time.**

---

## Why

Useful for expensive reports that are queried repeatedly.

---

## Analogy

Instead of calculating monthly sales every morning,

calculate once,

save the report,

and refresh it later.

---

## Syntax

```sql
CREATE MATERIALIZED VIEW monthly_sales AS

SELECT

DATE_TRUNC('month', order_date) AS month,

SUM(amount) AS total_sales

FROM orders

GROUP BY DATE_TRUNC('month', order_date);
```

Refresh

```sql
REFRESH MATERIALIZED VIEW monthly_sales;
```

---

## Execution

```text
Original Table

↓

Run Query Once

↓

Store Result

↓

Users Read Stored Data
```

---

## Drawbacks

* Consumes storage
* Data becomes stale until refreshed
* Refresh operation has a cost

---

## Views vs Materialized Views

| Feature       | View      | Materialized View |
| ------------- | --------- | ----------------- |
| Stores Data   | ❌ No      | ✅ Yes             |
| Stores Query  | ✅ Yes     | ✅ Yes             |
| Always Latest | ✅ Yes     | ❌ No              |
| Faster Reads  | ❌ Depends | ✅ Yes             |
| Needs Refresh | ❌ No      | ✅ Yes             |

---

## Quick Revision

View

↓

Virtual Table

---

Materialized View

↓

Stored Result

---

View

↓

Always Current

---

Materialized View

↓

Refresh Required
